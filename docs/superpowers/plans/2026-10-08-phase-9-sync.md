# Phase 9 — Sync framework & Health Connect (M6) Implementation Plan

**Goal:** Build the `SyncProvider` API (§7.1), the `SyncEngine` with snapshot-then-tail backfill (§7.2, §7.3),
change-log compaction (§7.4), and the first provider, Health Connect (§7.5). Then close Phase 9's three exit
criteria on the real phone: enabling Health Connect backfills all history, new records reach Health Connect
within minutes of a watch sync, and forced retries create no duplicates.

**Spec:** `docs/implementation-plan.md` §7 (all of it), §5.4 (change log), §8.7 (`SyncEngineWorker`,
`MaintenanceWorker`), §11 (SyncEngine tests), §12 Phase 9.

## Architecture

```
:core:sync-api            SyncProvider, RecordType, Readiness, RecordChange, PushOutcome  (pure Kotlin)
:core:sync-healthconnect  HealthConnectSyncProvider (+ record mapper, permissions)       @IntoSet
:core:data                SyncEngine, SyncEngineWorker, SyncRepository, SyncPrefs,
                          ChangeLogCompactor, MaintenanceWorker, SyncScheduler
:core:database            SyncCursorDao, change-log range/compaction queries, findByIds/count per table
:app                      Data tab "Connected services" card, HC permission launcher, rationale activity
```

- **Provider state lives in two places, on purpose.** `SyncPrefs` (DataStore) holds which providers the user has
  switched on. The `sync_cursor` row holds sync progress: `last_seq`, `snapshot_state` (non-null while the
  backfill runs), `last_success_at`, `last_error`. There's no schema change, so no migration.
- **Turning a provider off deletes its cursor**, so turning it back on starts a fresh backfill. A **Fatal**
  outcome only removes the provider from the enabled set and keeps the cursor, so "Reconnect" resumes where it
  stopped. Compaction honours every cursor row, which covers both.
- **Snapshot (§7.3).** On the first run the engine writes a cursor with `last_seq = MAX(change_log.seq)` and a
  JSON `snapshot_state` (`type`, `afterId`, `pushed`, `total`). It walks each supported table by primary key in
  pages of 500 and saves the state after every page, so an interrupted backfill resumes. Snapshot changes carry
  `seq = 0`.
- **Tail (§7.2).** The engine reads `head = MAX(seq)`, then the change log over `(cursor, head]` filtered to the
  provider's types, 500 rows at a time. Repeated entries for the same record collapse into one, and each record
  is loaded at its *current* version. A `deleted` row becomes `Op.DELETE`. When a batch succeeds the cursor moves
  to the batch's last seq. Once the log is drained it moves to `head`, so skipped unsupported types don't pin
  compaction. SQLite has a single writer, so every seq ≤ `MAX(seq)` is already committed.
- **Outcomes.** `Success` → advance and loop. `Retry(after)` → `Result.retry()` (exponential backoff), or a
  delayed re-enqueue when `after` is set. `Fatal` → disable the provider and record the reason. A provider that
  isn't `Ready` records why and ends successfully; it's tried again on the next ingest or periodic run.
- **Scheduling.** `SyncEngineWorker` runs as unique work `sync-{id}` with `KEEP` after every ingest (from
  `HealthSyncCoordinator`) and after an import, plus `sync-{id}-periodic` every 6 h, both under the provider's
  constraints. `MaintenanceWorker` runs daily while idle and charging: it prunes the journal and compacts the
  change log.
- **Compaction (§7.4).** Delete `seq ≤ MIN(last_seq)` over all cursor rows, or the whole log when there are none.
  Seqs are `AUTOINCREMENT`, so a compacted log never reuses one.

## Health Connect mapping (§7.5)

| Canonical | Health Connect | clientRecordId |
|---|---|---|
| Step interval | `StepsRecord`, plus `DistanceRecord` and `ActiveCaloriesBurnedRecord` when > 0 | `id`, `id/distance`, `id/energy` |
| Heart rate sample | `HeartRateRecord` with one sample | `id` |
| SpO2 | `OxygenSaturationRecord` | `id` |
| Blood pressure | `BloodPressureRecord` | `id` |
| Sleep session | `SleepSessionRecord` with stages | `id` |
| Workout | `ExerciseSessionRecord` (+ `ExerciseRoute`), workout HR series as one `HeartRateRecord` | `id`, `id/hr` |

`clientRecordVersion` = the record's `version`, so a corrected sleep night overwrites its earlier copy.

- **Heart rate is not grouped into series (deviation from §7.5).** A series assembled from whatever samples
  happen to share a change batch would overwrite earlier samples of the same window with a partial copy. One
  record per sample keeps one deterministic ID per fact, and that's what makes pushes idempotent. Workout HR
  *is* a series, because a workout's HR is written once, with the workout.
- **Temperature and stress aren't pushed.** The GTR 3 Pro doesn't report either (recon), and Health Connect has
  no stress type.
- **Workouts map to `EXERCISE_TYPE_OTHER_WORKOUT`.** The SDK documents no sport-type table, and no workout has
  been recorded on the real watch yet. Leaving the type unmapped is a documented gap; a guessed mapping would be
  wrong without anyone noticing.
- **Readiness** requires the Health Connect SDK to be available and *all* write permissions to be granted. A
  partial grant would let the cursor run past changes the provider couldn't write.
- **Errors.** `SecurityException` → `Fatal("Health Connect permission revoked")`. Anything else → `Retry`.
  Records Health Connect would reject (for example, zero steps or `start == end`) are filtered out by the
  mapper. If an insert still fails with `IllegalArgumentException`, the batch is retried one record at a time
  and the rejected ones are skipped, so one bad row can't stall the provider.

## On-device verification

1. Install the debug build over the existing install so the real synced history stays. Note the local record
   counts.
2. Enable Health Connect and grant permissions. When the card shows "Up to date", the audit's per-type counts must
   equal the local counts (step intervals with zero steps excluded).
3. Sync the watch. Without opening the app, the audit must show the new records within minutes.
4. Force retries: use the debug "Re-send everything" action (it deletes the cursor, so the next run is a fresh
   backfill), and kill the process mid-backfill. Afterwards the audit must show total == distinct
   clientRecordIds and the same counts as step 2.
